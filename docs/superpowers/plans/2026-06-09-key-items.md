# Key Items Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add "key" items — story-progression items that occupy no inventory slot, cannot be destroyed, and move only by direct character-to-character transfer — and let authors gate scenes on key possession through the existing precondition system.

**Architecture:** A key is a distinct `ItemType`. Keys live in a separate `keys` compartment on the `Inventory` object (parallel to `items`), so slot math never sees them. Mobility is constrained by guards placed where each illegal move occurs (drop, loot-stow). Gating is **not** a new subsystem: authors write ordinary scene preconditions that scan `room.occupants` for a key via the public `inventory.keys` / `keyCode` surface, and the engine exposes `Character.consumeKey` as the only sanctioned way to spend a one-shot key.

**Tech Stack:** TypeScript (strict, NodeNext), Vitest, ESLint. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-06-09-key-items-design.md`

```ts
   * keyring-to-keyring move is the only way a key changes hands. The recipient
   * records it as a single `pickUp`; the giver's side is silent (it is not a drop).

   * @param recipient - The character receiving the key.

  transferKey(key: IItem, recipient: ICharacter) {

      throw new ProceduralViolation(

      );

    this.relinquishItem(key);
    recipient.addToInventory(key);
  }
```

```ts
  putInLootBox(lootBox: ILoot, item: IItem | IItem[]): IItem[] {
    this.#requireCoLocated(lootBox);

    if (requested.some((i) => i.type === "key")) {

        "Keys cannot be stored in a loot container.",
      );

    const toPut = present.slice(0, free);
    if (toPut.length > 0) {

        lootBox.stowItem(putItem);
      }
    }
```

## Task 10: Gating pattern — a scene precondition that checks for a key

This task adds **no source change**. It proves the spec's central claim — that keys "hook into scene preconditions" using only the public surface (`inventory.keys`, `keyCode`, `room.occupants`) — and documents the intended authoring pattern as an executable example.

**Files:**
- Test: `src/lib/scene.test.ts`

- [ ] **Step 1: Write the test**

In `src/lib/scene.test.ts`, add imports for the real `Character` and `createKey`, plus the shared stat/campaign helpers:


Then add this `describe` block at the end of the top-level `describe("Scene", ...)` (before its closing `});`):

```ts
  describe("key-gated scene (authoring pattern)", () => {
    // A precondition an author writes with the public surface: the gate opens
    // when any occupant of the room holds a key with the matching code.
    const requiresKey = (keyCode: string) => (room: IRoom) =>
      room.occupants.some((c) =>
        c.inventory.keys.some((k) => k.keyCode === keyCode),
      );

    function roomWithOccupants(occupants: Character[]): IRoom {
      return { occupants } as unknown as IRoom;
    }

    it("does not fire when no occupant holds the key", () => {
      const { scene, script } = makeScene({
        preconditions: [requiresKey("vault")],
      });
      const bystander = new Character(makeCampaign(), "Bystander", makeStats());

      scene.playScene("enter", roomWithOccupants([bystander]));

      expect(script).not.toHaveBeenCalled();
    });

    it("fires once an occupant holds the matching key", () => {
      const { scene, script } = makeScene({
        preconditions: [requiresKey("vault")],
      });
      const hero = new Character(makeCampaign(), "Hero", makeStats());
      hero.addToInventory(createKey({ name: "Vault Key", keyCode: "vault", consumeOnUse: false }));

      const room = roomWithOccupants([hero]);
      scene.playScene("enter", room);

      expect(script).toHaveBeenCalledOnce();
      expect(script).toHaveBeenCalledWith(room);
    });
  });
```
